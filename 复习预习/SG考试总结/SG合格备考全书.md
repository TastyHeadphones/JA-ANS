## 0. 考试地图与学习方法

### 0.1 先纠正一个重要误区

现行 CBT 是**科目 A 与科目 B 合计 120 分钟、合计 60 问**。合格判定使用 IRT 评价分，科目 A、科目 B 各须达到 600/1000；这不是简单地“答对 60% 就一定合格”。把 60% 当学习目标可以，但模考应争取 **75%～80%**，为题目难度和读解失误留余量。

### 0.2 得分优先顺序

| 优先级 | 内容 | 学到什么程度 |
|---|---|---|
| S | CIA、风险、ISMS、攻击与对策、法务 | 能区分相邻概念，看到关键词即选 |
| A | 事件响应、认证密码、审计、网络 | 会流程顺序、用途和典型案例 |
| B | 服务管理、项目管理、企业战略 | 记高频术语，不深挖计算 |
| C | 冷门协议细节、复杂算法、条文号 | 知道存在即可，果断跳过 |

### 0.3 日语题干的“方向盘”

| 日语 | 读音 | 中文 | 考场动作 |
|---|---|---|---|
| 最も適切なもの | もっともてきせつなもの | 最恰当的一项 | 不找“也对”，找最完整的一项 |
| 適切でないもの | てきせつでないもの | 不恰当的一项 | 圈出否定，避免反选 |
| 最初に行う | さいしょにおこなう | 最先做 | 先遏制/确认，再追责和永久修复 |

| 再発防止 | さいはつぼうし | 防止复发 | 找原因、规则、技术或流程的永久改进 |
| 直ちに | ただちに | 立即 | 优先降低正在扩大的损害 |
| あらかじめ | あらかじめ | 预先 | 事前规则、同意、备份或演练 |
| ～に限る | ～にかぎる | 仅限于 | 检查选项是否越权或范围过宽 |

**通用判断链**：资产是什么 → 威胁利用哪个漏洞 → 损害 CIA 哪一项 → 应采取预防、检测、遏制、恢复中的哪一步。

## 1. 情報セキュリティ基础 / 信息安全基础

### 1.1 必背术语

| 日文术语 | 假名读音 | 中文对应 | 一句话解释 | 考频 | 易错点 |
|---|---|---|---|---|---|
| 機密性 | きみつせい | 保密性 | 只让获授权者访问 | ★★★ | 不是“内容正确” |
| 完全性 | かんぜんせい | 完整性 | 信息未被非法篡改或破坏 | ★★★ | 日语“完全”不是可用性 |
| 可用性 | かようせい | 可用性 | 需要时能正常使用 | ★★★ | 日语读作かようせい |
| 真正性 | しんせいせい | 真实性 | 主体或信息确为其所声称者 | ★★ | 与完整性相邻 |
| 責任追跡性 | せきにんついせきせい | 可追责性 | 行为能追溯到责任主体 | ★★ | 靠日志与唯一账号 |
| 否認防止 | ひにんぼうし | 不可否认性 | 防止事后否认发送或操作 | ★★ | 数字签名典型用途 |
| 信頼性 | しんらいせい | 可靠性 | 系统行为与结果稳定可信 | ★★ | 不等同可用性 |
| 情報資産 | じょうほうしさん | 信息资产 | 数据及承载、处理它的资源 | ★★★ | 人员、纸张也可算资产 |
| 脅威 | きょうい | 威胁 | 可能造成损害的原因 | ★★★ | 攻击者、灾害、误操作 |
| 脆弱性 | ぜいじゃくせい | 漏洞/薄弱点 | 可被威胁利用的弱点 | ★★★ | 不是损失本身 |
| リスク | — | Risk / 风险 | 威胁利用漏洞造成影响的可能性 | ★★★ | 与威胁不能互换 |
| セキュリティインシデント | — | Security incident / 安全事件 | 破坏或可能破坏安全的事件 | ★★★ | 不必等到确认损害 |

### 1.2 三秒判别

- **泄露、偷看、误发** → 機密性。
- **篡改、错误更新、假数据** → 完全性。
- **宕机、DDoS、灾害后不能用** → 可用性。
- **“谁操作的”查不出** → 責任追跡性；**“我没发过”** → 否認防止。
- **危险源**是脅威，**可乘之隙**是脆弱性，**两者结合造成损失的可能性**是リスク。

### 1.3 信息分级与生命周期

信息应经历 `生成/取得 → 利用 → 保存 → 传输/共享 → 归档 → 废弃`。每一步按分类（公开、内部、机密等）规定负责人、访问权限、保存期限、传输方式和销毁方法。废纸进普通垃圾桶、旧磁盘只“删除文件”、离职账号不停止，都是高频错误。

## 2. 脅威・脆弱性・攻撃手法 / 威胁、漏洞与攻击

|---|---|---|---|---|

| ワーム | Worm | 蠕虫 | 无须寄生、自我网络传播 | ★★★ |
| トロイの木馬 | Trojan horse | 木马 | 伪装正常，不自我复制 | ★★★ |

| ルートキット | Rootkit | Rootkit / 隐匿工具包 | 隐藏入侵痕迹和恶意程序 | ★ |
| バックドア | Backdoor | 后门 | 绕过正常认证再次进入 | ★★★ |
| フィッシング | Phishing | 网络钓鱼 | 假网站、假邮件骗凭据 | ★★★ |
| スミッシング | Smishing | 短信钓鱼 | SMS 中的恶意链接 | ★★ |
| ビッシング | Vishing | 电话语音钓鱼 | 电话冒充客服等 | ★ |
| 標的型攻撃 | ひょうてきがたこうげき | 定向攻击 | 针对特定组织长期潜伏 | ★★★ |
| 水飲み場型攻撃 | みずのみばがたこうげき | 水坑攻击 | 篡改目标常访问的网站 | ★★ |
| ソーシャルエンジニアリング | Social engineering | 社会工程 | 利用人的心理而非技术漏洞 | ★★★ |
| ショルダーハッキング | Shoulder surfing | 肩窥 | 从背后偷看屏幕/键盘 | ★★ |
| トラッシング | Trashing | 垃圾搜寻 | 从废弃物取得机密 | ★★ |

### 2.2 网络与 Web 攻击

| 攻击 | 中文 | 题干特征 | 首要对策 |
|---|---|---|---|
| パスワードリスト攻撃 | 撞库攻击 | 使用别处泄露的 ID/密码组合 | MFA、密码不复用 |
| ブルートフォース攻撃 | 暴力破解 | 尝试所有组合 | 锁定、限速、MFA |
| 辞書攻撃 | じしょこうげき / 字典攻击 | 尝试常见单词 | 长且不易猜的密码 |
| リバースブルートフォース | 反向暴力破解 | 固定常见密码，换大量账号 | MFA、异常检测 |
| SQLインジェクション | SQL 注入 | 输入值被拼入 SQL | 参数化查询 |
| OSコマンドインジェクション | OS 命令注入 | 输入值被当系统命令执行 | 不调用 shell、严格验证 |
| クロスサイトスクリプティング（XSS） | 跨站脚本 | 恶意脚本在用户浏览器执行 | 输出转义 |
| CSRF | 跨站请求伪造 | 借已登录会话执行非本人意图操作 | CSRF token、再认证 |
| ディレクトリトラバーサル | 目录遍历 | `../` 读取目录外文件 | 固定路径、规范化与校验 |
| セッションハイジャック | 会话劫持 | 窃取 session ID 冒充用户 | TLS、ID 更新、安全 Cookie |
| DoS攻撃 | 拒绝服务 | 单一来源压垮服务 | 限速、过滤、冗余 |
| DDoS攻撃 | 分布式拒绝服务 | 大量被控主机同时攻击 | 清洗服务、CDN、上游协作 |
| DNSキャッシュポイズニング | DNS 缓存投毒 | 错误域名解析被缓存 | DNSSEC、随机化查询 |
| 中間者攻撃 | ちゅうかんしゃこうげき / 中间人攻击 | 窃听并可能篡改双方通信 | 证书验证、TLS |
| リプレイ攻撃 | Replay / 重放攻击 | 重发截获的认证数据 | nonce、时间戳、一次性值 |
| ゼロデイ攻撃 | Zero-day / 零日攻击 | 修补程序发布前利用漏洞 | 分层防御、行为检测、缓解措施 |
| サプライチェーン攻撃 | 供应链攻击 | 从委托方、软件更新或供应商侵入 | 供应商管理、SBOM、签名验证 |

### 2.3 最容易混淆

- **XSS vs CSRF**：XSS 是“网站吐出恶意脚本”；CSRF 是“借你的登录状态替你下命令”。
- **病毒 vs 蠕虫 vs 木马**：寄生复制 / 独立自传 / 伪装潜入。
- **撞库 vs 暴力破解**：拿泄露组合试 / 穷举组合。
- **水坑 vs 钓鱼**：等目标去常用网站 / 主动诱导目标点假链接。

## 3. 情報セキュリティ対策 / 信息安全对策

### 3.1 人、物理、技术三分类

| 分类 | 典型措施 | 常见错误选项 |
|---|---|---|
| 人的対策 | 教育、誓约、职责分离、背景核查、举报制度 | 把防火墙说成人的措施 |
| 物理的対策 | 门禁、锁、监控、防灾、屏蔽、设备固定 | 把登录认证说成物理措施 |
| 技術的対策 | 认证、访问控制、加密、日志、EDR、WAF | 把员工培训说成技术措施 |

### 3.2 高频技术措施

| 术语 | 原词/读音 | 中文与用途 | 考频 |
|---|---|---|---|
| ファイアウォール | Firewall | 按规则控制网络通信 | ★★★ |
| WAF | Web Application Firewall | 检测/阻断针对 Web 应用的攻击 | ★★★ |
| IDS | Intrusion Detection System | 检测入侵并告警，不主动阻断 | ★★★ |
| IPS | Intrusion Prevention System | 检测并主动阻断 | ★★★ |
| EDR | Endpoint Detection and Response | 终端行为监测、调查与响应 | ★★★ |
| アンチウイルス | Antivirus | 特征码/行为等检测恶意软件 | ★★★ |
| サンドボックス | Sandbox | 在隔离环境运行可疑对象 | ★★ |
| プロキシサーバ | Proxy server | 代理访问，可过滤并留日志 | ★★ |
| DLP | Data Loss Prevention | 识别并阻止敏感数据外泄 | ★★ |
| SIEM | Security Information and Event Management | 汇总关联分析日志与告警 | ★★★ |
| SOC | Security Operation Center | 持续监视、分析与响应的组织/功能 | ★★★ |

| VPN | Virtual Private Network | 在公共网络建立受保护通道 | ★★★ |
| パッチ管理 | Patch management | 评估、测试、部署和确认修补 | ★★★ |
| 脆弱性診断 | ぜいじゃくせいしんだん | 扫描/检查已知弱点 | ★★★ |
| ペネトレーションテスト | Penetration test | 经授权模拟攻击验证可利用性 | ★★ |

### 3.3 设计原则

- **最小権限の原則（さいしょうけんげん）**：只给完成任务所需的最少权限。
- **職務分掌（しょくむぶんしょう）**：申请、批准、执行、复核分开，防止单人舞弊。
- **多層防御（たそうぼうぎょ）**：入口、网络、终端、数据多层拦截，不依赖单点。
- **フェールセーフ**：故障时转到安全状态，例如门禁系统故障后按生命安全设计解锁。
- **フェールソフト**：部分故障时降低功能继续服务。
- **フールプルーフ**：防止误操作，例如危险按钮加确认。
- **セキュアバイデザイン**：从设计阶段纳入安全，而非上线后补救。
- **ゼロトラスト**：不因位于内网就默认信任；持续验证主体、设备和上下文。

### 3.4 备份必考结论

`3-2-1`：至少 3 份数据、2 种介质、1 份异地/离线。备份不是“做完就行”，必须定期做**恢复测试**。勒索软件场景中，始终在线且同域可写的备份也可能一起被加密。

## 4. 情報セキュリティ管理・ISMS / 信息安全管理

### 4.1 ISMS 骨架

ISMS 是组织基于风险持续管理信息安全的体系，不是“一套安全产品”。最高管理者确定方针并提供资源；管理责任不能全部甩给信息系统部门。

| 术语 | 读音/原词 | 中文 | 三秒判别 | 考频 |
|---|---|---|---|---|
| 情報セキュリティ方針 | じょうほうセキュリティほうしん | 信息安全方针 | 最高层方向与承诺 | ★★★ |
| 情報セキュリティ目的 | もくてき | 安全目标 | 可衡量、与方针一致 | ★★ |
| 適用範囲 | てきようはんい | 适用范围 | 明确哪些组织/地点/系统纳入 | ★★★ |
| リスクアセスメント | Risk assessment | 风险评估 | 识别、分析、评价 | ★★★ |
| リスク対応 | Risk treatment | 风险处置 | 选择措施处理风险 | ★★★ |
| 管理策 | かんりさく | 控制措施 | 改变风险的措施 | ★★★ |
| 適用宣言書 | てきようせんげんしょ | 适用性声明（SoA） | 说明选了哪些控制及理由 | ★★★ |
| 内部監査 | ないぶかんさ | 内部审核 | 独立检查 ISMS 是否符合且有效 | ★★★ |
| マネジメントレビュー | Management review | 管理评审 | 最高管理者审查并决定改进 | ★★★ |
| 是正処置 | ぜせいしょち | 纠正措施 | 消除不符合的原因、防止再发 | ★★★ |
| 継続的改善 | けいぞくてきかいぜん | 持续改进 | 反复评价和改进体系 | ★★★ |

### 4.2 规则层级

`方針（为什么/大方向） → 規程・基準（必须遵守什么） → 手順（具体怎么做） → 記録（证明做过）`。题目若问最高管理者公开的基本姿态，选方针；若问操作顺序，选手顺。

### 4.3 PDCA 如何考

- **Plan**：范围、方针、风险评估、风险处置计划。
- **Do**：实施控制、教育、运行。
- **Check**：监视测量、内部审核、管理评审。
- **Act**：纠正、不符合处理、持续改进。

### 4.4 人员与委托方管理

- 入职前明确保密义务；在职按岗位培训；调岗立即复核权限；离职及时回收证件、设备并停用账号。
- 外包不能把最终管理责任一起外包。合同应写明安全要求、再委托、事件报告、审计权、数据返还/销毁和结束时处置。
- 云服务采用**责任共有模型**：服务商负责的范围依服务模式与合同而变，用户始终要管好数据、账号、配置和使用方式。

## 5. リスクマネジメント / 风险管理

### 5.1 评估流程

1. **リスク特定**：找出资产、威胁、漏洞、既有措施和可能后果。
2. **リスク分析**：估计发生可能性和影响，求风险等级。
3. **リスク評価**：与风险准则比较，决定是否需要处置及优先级。
4. **リスク対応**：选择规避、降低、转移/共有或保有。
5. 沟通协商、监视评审贯穿全程。

### 5.2 四类处置

| 日文 | 读音 | 中文 | 典型例子 |
|---|---|---|---|
| リスク回避 | かいひ | 风险规避 | 停止高风险业务/功能 |
| リスク低減 | ていげん | 风险降低 | 加 MFA、补丁、教育 |
| リスク移転・共有 | いてん・きょうゆう | 风险转移/分担 | 保险、合同分担损失 |
| リスク保有・受容 | ほゆう・じゅよう | 风险保留/接受 | 成本高于收益时批准接受 |

**陷阱**：买保险不会让事件发生概率降低，只转移部分财务影响；外包也不会消灭本组织的责任。

### 5.3 定量词

| 术语 | 含义 | 记法 |
|---|---|---|
| SLE（Single Loss Expectancy） | 单次损失期望 | 资产价值 × 损失比例 |
| ARO（Annual Rate of Occurrence） | 年发生率 | 一年预计发生次数 |
| ALE（Annual Loss Expectancy） | 年损失期望 | SLE × ARO |
| 残留リスク | ざんりゅうリスク / 残余风险 | 控制后仍留下的风险 |
| リスク所有者 | しょゆうしゃ / 风险所有者 | 有权限并负责管理某风险的人 |

例：资产 1000 万日元，一次损失 20%，五年一次，则 SLE=200 万，ARO=0.2，ALE=40 万日元/年。措施年成本远高于减少的年损失时，要结合定性影响再判断，不能机械购买。

### 5.4 风险分析方法

- **定量分析**：用金额、概率等数字，便于成本比较，但输入常不精确。
- **定性分析**：用高/中/低矩阵，快速且易沟通，但主观性强。
- **ベースラインアプローチ**：采用业界基准控制，快但可能不贴合个别风险。
- **詳細リスク分析**：逐资产详细分析，准确但成本高。

### 6.2 个人信息高频概念

| 概念 | 中文结论 | 易错点 |
|---|---|---|
| 個人情報 | 关于生存个人且可识别特定个人的信息 | 单独不能识别但可容易核对其他信息也可能算 |
| 個人データ | 构成个人信息数据库等的个人信息 | 范围比“个人信息”窄 |
| 保有個人データ | 事业者有权披露、订正等的个人数据 | 与全部个人数据不等同 |
| 要配慮個人情報 | 需特别照顾，避免歧视等的信息 | 种族、信条、病历等；取得原则需本人同意 |
| 個人識別符号 | 能识别个人的符号 | 生物特征编码、护照号等 |
| 匿名加工情報 | 无法识别且不能复原的加工信息 | 与假名加工不同 |
| 仮名加工情報 | 用其他描述替换部分信息 | 保留对照信息时仍可能复原 |
| 第三者提供 | 向本组织外第三方提供 | 原则需同意，但法定例外存在 |
| 委託 | 在利用目的范围内委托处理 | 通常不按第三方提供处理，但须监督委托方 |
| 漏えい等報告 | 泄露等报告 | 符合法定重大情形时向委员会报告并通知本人 |

### 6.3 营业秘密三要件

1. **秘密管理性**：组织客观显示其作为秘密管理（权限、标识等）。
2. **有用性**：对经营活动有用，不包括违法秘密。
3. **非公知性**：公众一般无法取得。

缺一就难以作为“営業秘密”保护。不是“公司觉得秘密”就自动成立。

### 6.4 著作权三秒判断

- 保护**表达**，不垄断思想、算法、事实本身。
- 著作权通常在创作时自动产生，不以登记为成立要件。
- 公司业务中职务创作的软件，在满足法律条件时法人可成为作者。
- 买正版软件不等于取得任意复制、改编和再发布权。

### 6.5 合同与合规

- **NDA（秘密保持契約）**：规定秘密范围、用途、接触者、期限、返还销毁和违约。
- **SLA**：约定服务水平、指标、测定和未达成时处理；不是安全保证书。
- **ライセンス**：确认使用人数、设备、复制、修改、再分发条件；开源软件也有许可义务。
- **コンプライアンス**不只守法，也包括内部规则、合同和社会规范。

## 7. インシデント対応・事業継続 / 事件响应与业务连续性

### 7.1 响应顺序

`准备 → 检测/通报 → 初动判断 → 遏制 → 根除 → 恢复 → 事后复盘与再发防止`

| 阶段 | 要做什么 | 不要做什么 |
|---|---|---|
| 準備 | 联系网、日志、工具、演练、备份 | 出事后才找负责人 |
| 検知・分析 | 保留证据，判断范围与严重性 | 未确认就对外断言 |
| 封じ込め | 隔离终端、封锁账号、限制通信 | 为找原因放任损害扩大 |
| 根絶 | 删除恶意程序、修漏洞、消除后门 | 只重启便宣布结束 |
| 復旧 | 从可信备份恢复、监视复发 | 未验证就全部上线 |
| 事後対応 | 查根因、更新规则、报告和教育 | 只处罚当事人 |

**证据保全**：记录谁在何时以何方式取得和交接证据（chain of custody）。不要随意关机、改文件或运行会覆盖大量日志的操作；具体动作依响应手顺和专家判断。

### 7.2 BCP/BCM 与灾难恢复

| 术语 | 原词 | 中文 | 必背结论 |
|---|---|---|---|
| BCM | Business Continuity Management | 业务连续性管理 | 持续管理的整体体系 |
| BCP | Business Continuity Plan | 业务连续性计划 | 发生中断时的具体计划 |
| BIA | Business Impact Analysis | 业务影响分析 | 找关键业务、影响和恢复优先级 |
| RTO | Recovery Time Objective | 恢复时间目标 | 最长可接受停机时间 |
| RPO | Recovery Point Objective | 恢复点目标 | 最多可容忍丢失多久的数据 |
| MTPD | Maximum Tolerable Period of Disruption | 最大可容忍中断时间 | RTO 原则上应短于它 |
| DR | Disaster Recovery | 灾难恢复 | 重点恢复 IT 基础设施与数据 |

例：RPO=1 小时表示最多接受丢失最近 1 小时的数据；RTO=4 小时表示目标在中断后 4 小时内恢复。**RPO 不是恢复耗时**。

### 7.3 备用站点

- **ホットサイト**：设备和数据近实时准备，恢复最快、成本最高。
- **ウォームサイト**：部分准备，速度与成本居中。
- **コールドサイト**：主要提供场地与基础设施，恢复慢、便宜。

演练形式：桌面推演、模拟演练、部分切换、全面切换。计划没有演练就无法确认可用性。

## 8. システム監査・内部統制 / 系统审计与内部控制

### 8.1 审计原则

| 术语 | 读音 | 中文 | 判别 |
|---|---|---|---|
| 独立性 | どくりつせい | 独立性 | 不审自己负责的工作 |
| 客観性 | きゃっかんせい | 客观性 | 以事实和证据判断 |
| 監査証拠 | かんさしょうこ | 审计证据 | 支撑结论，须充分且适切 |
| 監査調書 | かんさちょうしょ | 审计工作底稿 | 记录过程、证据和判断 |
| 監査報告書 | かんさほうこくしょ | 审计报告 | 向适当管理层报告发现与意见 |
| フォローアップ | Follow-up | 后续跟踪 | 确认改善是否落实 |

审计员评价和提出建议，但**不替被审计部门设计、批准或执行改善**，否则损害独立性。最终是否接受风险由管理者决定。

### 8.2 审计技术

- **ヒアリング**：快，但口头说明单独证据力弱。
- **閲覧**：检查规则、合同、日志、记录。
- **観察**：现场看实际操作，注意被观察者可能改变行为。
- **再実施**：审计员独立重做控制，证据力较强。
- **突合**：把不同来源记录相互核对。

### 8.3 内部控制

目标通常围绕业务有效性与效率、报告可靠性、守法合规、资产保全。控制分为：

- **予防的統制**：事前防止，如审批、权限分离、输入校验。
- **発見的統制**：事后/过程中发现，如日志复核、盘点、异常告警。
- **訂正的統制**：发现后修正，如备份恢复、错误数据更正。

## 9. 暗号・認証技術 / 密码与认证技术

### 9.1 密码基础

| 术语 | 中文 | 优点 | 陷阱 |
|---|---|---|---|
| 共通鍵暗号方式 | 对称密码 | 快，适合大量数据 | 密钥配送困难 |
| 公開鍵暗号方式 | 非对称密码 | 便于密钥分发、可签名 | 慢，不直接替代所有对称加密 |
| ハイブリッド暗号 | 混合加密 | 公钥保护会话密钥，对称加密正文 | TLS 等常见思路 |
| ハッシュ関数 | 哈希函数 | 单向、固定长度、检验变更 | 不是可解密的加密 |
| ソルト | Salt / 盐 | 每个密码加随机值再哈希 | 防彩虹表，不代替慢哈希 |
| 電子署名 | 数字签名 | 完整性、真实性、不可否认 | 不提供正文保密 |
| 電子証明書 | 数字证书 | 把公钥与主体绑定 | 须验证有效期、链和撤销状态 |
| PKI | Public Key Infrastructure | 公钥基础设施 | CA、证书、撤销等整体机制 |

### 9.2 数字签名过程

发送者用**自己的私钥**对消息摘要签名；接收者用**发送者的公钥**验证。若要保密给接收者，则用**接收者的公钥**加密，接收者用自己的私钥解密。

口诀：**签名私钥签、公钥验；保密公钥锁、私钥开。**

### 9.3 认证三要素

| 要素 | 日语 | 例子 |
|---|---|---|
| 知识 | 知識情報（ちしきじょうほう） | 密码、PIN |
| 持有 | 所持情報（しょじじょうほう） | IC 卡、手机、硬件令牌 |
| 生体 | 生体情報（せいたいじょうほう） | 指纹、面部、虹膜 |

两个密码仍是同一要素，不叫多因素认证。**二段階認証**强调步骤数，**多要素認証**强调不同要素，不能混同。

### 9.4 生物认证指标

- **FAR（他人受入率）**：把别人错认成本人；越低越安全。
- **FRR（本人拒否率）**：把本人拒绝；越低越好用。
- 阈值调严通常 FAR 降、FRR 升，两者存在权衡。

### 9.5 访问控制模型

- **DAC**：资源所有者决定权限。
- **MAC**：系统按安全级别强制控制。
- **RBAC**：按角色赋权，岗位管理高频。
- **ABAC**：按用户、资源、环境等属性动态判断。
- **SSO**：一次认证访问多个系统；便利但认证点失陷影响大，需强化 MFA 和可用性。

## 10. ネットワーク・システム基礎 / 网络与系统基础

### 10.1 协议速查

| 协议 | 用途 | 安全提示 | 考频 |
|---|---|---|---|
| IP | 寻址与分组传送 | 本身不保证送达 | ★★★ |
| TCP | 可靠、面向连接传输 | 三次握手 | ★★★ |
| UDP | 无连接、开销小 | 不保证顺序与到达 | ★★ |
| HTTP / HTTPS | Web / 经 TLS 保护的 Web | HTTPS 不代表网站内容一定善意 | ★★★ |
| DNS | 域名解析 | 可遭缓存投毒、隧道滥用 | ★★★ |
| DHCP | 自动分配网络参数 | 防伪 DHCP | ★★ |
| SMTP | 发送邮件 | 配合 SPF/DKIM/DMARC | ★★★ |
| POP3 / IMAP | 收取 / 服务器同步邮件 | 优先加密连接 | ★★ |
| SSH | 加密远程登录 | 替代明文 Telnet | ★★★ |
| SNMP | 网络设备监控管理 | 使用安全版本并限制访问 | ★★ |
| NTP | 时间同步 | 日志关联依赖准确时间 | ★★ |

### 10.2 邮件认证

- **SPF**：域名声明哪些发送服务器获授权，主要检查信封发件域与来源 IP。
- **DKIM**：发送方用域名私钥给邮件签名，接收方用 DNS 公钥验证。
- **DMARC**：基于 SPF/DKIM 的对齐结果规定处理策略并提供报告。
- **S/MIME**：对邮件正文做加密/数字签名，解决的层面不同。

### 10.3 网络分区

- **DMZ**：放置需对外公开的服务器，使其与内部网隔离。
- **VLAN**：逻辑划分广播域；不是加密技术。
- **NAPT**：多个私有地址共享公网地址，不应当作完整防火墙。
- **无线 LAN**：优先 WPA3；企业认证结合 802.1X/RADIUS。隐藏 SSID、MAC 地址过滤不能替代强认证和加密。

### 10.4 云与虚拟化

| 模式 | 用户主要管理 | 服务商扩大的管理范围 |
|---|---|---|
| IaaS | OS、应用、数据、账号、配置 | 物理设施、硬件、虚拟化层 |
| PaaS | 应用、数据、账号、部分配置 | 再管理 OS 和运行环境 |
| SaaS | 数据、账号、租户配置和使用 | 再管理应用本身 |

**可用区冗余**防单一机房故障；跨区域备份应对区域灾害。快照不自动等于合格备份，仍要看隔离、保留和恢复验证。

### 10.5 开发安全

- 需求阶段定义安全要求；设计做威胁建模；编码遵守安全规范；测试含代码审查、SAST/DAST、渗透测试；上线后持续补丁和监视。
- **SAST**：不运行程序分析代码；**DAST**：对运行中的应用测试。
- 测试环境不应随意复制真实个人数据；必要时脱敏并实施同等控制。
- 变更须申请、影响评估、审批、测试、回退计划、实施和记录，开发者不应单独把代码直接推到生产。

| ERP | 企业资源计划 | 整合企业核心资源与业务数据 |
| KPI | 关键绩效指标 | 衡量目标达成过程的关键指标 |
| KGI | 关键目标指标 | 衡量最终目标是否达成 |
| DX | 数字化转型 | 用数字技术改变业务与组织竞争力 |
| コーポレートガバナンス | 公司治理 | 监督经营、保障利益相关者权益 |

### 11.4 计算题最低限度

- **稼働率（かどうりつ）** = 正常运行时间 ÷ 总时间。
- 串联系统全体可用率 = 各部分可用率相乘。
- 两个独立并联系统全停概率 = 各自故障率相乘；可用率 = 1 − 全停概率。
- **損益分岐点売上高** = 固定费 ÷ 边际贡献率；若题目复杂且耗时，先标记后做。

## 12. 科目 B 长文案例解题法

### 12.1 六步读法

1. **先读设问**：圈出「最初」「根本」「再発防止」「誰が」「何を」。
2. **画角色表**：负责人、系统管理员、委托方、员工各有什么权限和义务。
3. **画时间线**：正常状态 → 异常征兆 → 发现 → 已采取动作 → 当前问题。
4. **标规则与事实冲突**：规定写 A，现场做 B 的位置通常就是考点。
5. **判断响应阶段**：正在扩大时先遏制；稳定后再根因、恢复、改规则。
6. **用题干证据排除**：不要凭“现实中也可能”补设定。

### 12.2 四类常见问法

#### A. “最初に行うべき”

原则：保护生命 → 遏制正在扩大的损害 → 按规定通报和保全证据 → 调查 → 永久修复。不要第一步就处罚、公开详情或全盘重装。

#### B. “根本的な対策 / 再発防止策”

临时断网、换一台电脑是遏制/恢复；修漏洞、取消共享账号、改变审批、实施自动检查才更像根本措施。

#### C. “原因として最も適切”

只选题干明确支持的直接原因。区分：触发事件、漏洞、管理上的根因、造成的影响。

#### D. “規程に照らして”

题目给出的内部规定是本题世界的规则，即使你公司做法不同，也按题干规定判断。

### 12.3 典型案例秒判表

| 场景 | 立即措施 | 后续根本措施 |
|---|---|---|
| 终端疑似恶意软件通信 | 隔离网络并通报 | 调查入口、清除、补丁、规则改进 |
| 账号疑似被盗 | 停用/冻结、撤销会话 | MFA、重置凭据、查日志与影响范围 |
| 邮件误发 | 尽快撤回/联系并通报 | 审批、DLP、延迟发送、教育 |
| Web 被篡改 | 隔离或切换可信页面、保全证据 | 修漏洞、换凭据、可信备份恢复 |
| 勒索软件 | 隔离感染范围、启动响应 | 根除、离线备份恢复、入口封堵 |
| 供应商泄露 | 依合同通报、确认影响和遏制 | 监督、审计、合同和访问范围改进 |

### 12.4 时间分配

- 全卷 120 分钟，不要给科目 A 或 B 设死板独立时间。
- 第一轮：会的立即答；计算长、资料长的题标记。
- 科目 B 每个设问都必须回到原文找证据；两项纠结时比较谁更符合限定词。
- 最后预留时间检查否定词、未答题和标记题。CBT 操作以考场界面说明为准。

## Day 1：安全目标、资产与风险语言

### 高分补充

#### 安全属性不要只背 CIA

| 属性 | 题干信号 | 典型控制 | 常见误判 |
|---|---|---|---|
| 機密性 | 阅览、泄露、误发、窃听 | 加密、访问控制、遮蔽 | 备份主要不解决泄露 |
| 完全性 | 篡改、错误、未授权更新 | 哈希、签名、输入校验 | 加密不自动保证未被篡改 |
| 可用性 | 停止、延迟、灾害、过载 | 冗余、备份、容量管理 | 权限严不等于可用 |
| 真正性 | 冒充、伪造来源 | 认证、证书、签名 | “数据没变”仍可能来源是假 |
| 責任追跡性 | 共用账号、日志缺失 | 唯一 ID、时间同步、日志 | 只记操作而不保护日志仍不可靠 |
| 否認防止 | 否认发送/批准 | 数字签名、可信时间 | 普通密码登录证据力有限 |

#### 资产台账至少记录什么

资产所有者、保管位置、分类、允许使用者、依赖关系、备份要求、保存期限和销毁方式。资产所有者负责确定保护要求，不等于亲自运维。清单若不更新，风险评估会漏掉影子 IT、退役设备和外部共享数据。

### 今日原创题

**1.** 顧客データが許可なく書き換えられた。直接損なわれた特性はどれか。
ア 機密性　イ 完全性　ウ 可用性　エ 責任追跡性

**2.** 共用 ID で管理システムを操作していたため、誤更新を行った者を特定できない。最も直接的に不足している特性はどれか。
ア 真正性　イ 可用性　ウ 責任追跡性　エ 機密性

**3.** 「未修正の OS」と「インターネット上の攻撃者」の組合せで、前者に該当するものはどれか。
ア 資産　イ 脅威　ウ 脆弱性　エ インシデント

**4.** 情報資産台帳の管理として最も適切なものはどれか。
ア 導入時だけ作成する　イ 機密情報だけ登録する　ウ 所有者と分類を定め変更時に更新する　エ 情報システム部だけが閲覧する

**5.** 暗号化したファイルのハッシュ値を安全に別管理する主目的の組合せはどれか。
ア 暗号化＝機密性、ハッシュ＝完全性　イ 暗号化＝可用性、ハッシュ＝機密性　ウ 両方＝可用性　エ 両方＝否認防止

## Day 2：恶意软件、钓鱼与人的弱点

### 高分补充

#### 侵入过程思维

`侦察 → 初始侵入 → 执行 → 权限提升 → 持久化 → 横向移动 → 收集/外传 → 破坏`。题目问对策时先判断攻击处于哪一步：邮件过滤防初始侵入，EDR 更擅长终端行为检测，网络分段限制横向移动，DLP 针对外传。

#### 钓鱼细分

- **スピアフィッシング**：针对特定个人/组织定制内容。
- **ホエーリング**：以高管等“大目标”为对象。
- **BEC（Business Email Compromise）**：冒充经营者或交易方诱导汇款、改收款账户。
- **QRコードフィッシング**：借二维码绕过对普通 URL 的观察或过滤。
- 培训不能单独解决全部问题，应结合邮件认证、过滤、MFA、汇款二次确认和便捷通报渠道。

### 今日原创题

**1.** 正規ソフトを装って利用者に実行させるが、自己増殖しないマルウェアはどれか。
ア ワーム　イ トロイの木馬　ウ ウイルス　エ ボットネット

**2.** 取引先役員を装い、振込先変更を急がせるメールへの最も有効な業務上の対策はどれか。
ア 添付を圧縮する　イ メールとは別経路で変更を確認する　ウ 全メールを印刷する　エ パスワードを毎日変更する

**3.** 標的社員が日常的に閲覧する業界サイトを改ざんして感染させる攻撃はどれか。
ア 水飲み場型攻撃　イ 辞書攻撃　ウ リプレイ攻撃　エ CSRF

## Day 4：防御体系、日志与终端

### 高分补充

#### 控制按时机分类

- **抑止的（Deterrent）**：警示牌、处罚规定，降低动机。
- **予防的（Preventive）**：MFA、审批、最小权限，阻止发生。
- **発見的（Detective）**：IDS、日志复核、盘点，发现异常。
- **訂正的（Corrective）**：修复配置、恢复数据，纠正结果。
- **代替的（Compensating）**：原控制不可行时用其他措施达到相近目的。

#### 日志管理

决定记录对象、保存期限、访问权限、时间同步、集中传送、完整性保护、监视频率和事件升级条件。日志越多不一定越好；没有时钟同步和关联规则，大量日志仍难调查。管理员也不应能无痕删除自己的操作记录。

## Day 6：风险评估、处置与数字

#### 风险矩阵的限制

## Day 7：法律、个人信息与知识产权

### 高分补充

#### 个人数据处理链

`明确利用目的 → 合法适当取得 → 目的范围内利用 → 准确性与安全管理 → 员工/委托方监督 → 依法提供 → 应对本人请求 → 到期安全删除`。同意不是所有处理的万能通行证；仍须遵守目的限制、安全管理和其他法定义务。

#### 第三方提供、委托与共同利用

- 第三方提供原则上需本人同意，但法律规定例外存在。
- 委托是在利用目的范围内让受托方处理，关键是选择和监督。
- 共同利用须事前通知或易于知悉共同利用项目、范围、目的和责任主体等。
- 跨境提供另有信息提供和持续确认等要求，考试中先看题干给定条件。

#### 不正访问的陷阱

未经许可使用他人 ID/密码进入受访问控制的系统是典型非法访问；帮助行为如提供识别符号、钓取或不当保管也可能受规制。获得口头“同事说可以”不等于系统管理者授权。

## Day 10：密码、认证、证书与访问控制

### 高分补充

#### 证书验证步骤

检查域名/主体匹配、有效期、签发链是否可信、签名是否有效、是否撤销。浏览器出现证书警告时，不应训练用户“一律继续”。私钥泄露后只换密码不够，应撤销旧证书并更换密钥。

#### 密码保存

服务器不应明文保存密码，也不应使用可逆加密作为常规验证方案；应使用带独立 salt、适合密码的慢哈希/KDF。Salt 可防相同密码得到相同结果和预计算表，但数据库泄露后仍需强密码、MFA 和合理成本参数。

### 今日原创题

**1.** 送信者の電子署名を検証する鍵はどれか。
ア 送信者の公開鍵　イ 送信者の秘密鍵を受信者へ渡す　ウ 受信者の秘密鍵　エ 共通パスワードだけ

**2.** 受信者だけが読めるよう公開鍵暗号で暗号化するとき用いる鍵はどれか。
ア 送信者の公開鍵　イ 受信者の公開鍵　ウ CA の秘密鍵　エ ハッシュ値

**3.** パスワードと PIN を順に入力する方式の説明はどれか。
ア 必ず多要素　イ 同じ知識要素なので多要素とは限らない　ウ 生体要素　エ 所持要素だけ

**4.** パスワードハッシュへ利用者ごとに salt を加える主目的はどれか。
ア 可用性をゼロにする　イ 同一パスワードや事前計算攻撃への耐性向上　ウ 復号可能にする　エ 通信速度向上

**5.** RBAC は何に基づくアクセス制御か。
ア 役割　イ 天気だけ　ウ ファイルサイズだけ　エ IP アドレスだけ

2. **イ**。接收者公钥锁，接收者私钥开。
3. **イ**。步骤多不等于要素多。

## Day 11：网络、邮件、无线与云

- TCP 端口不通：看防火墙、服务监听、路由。
- HTTPS 有证书警告：看主体、有效期、信任链。
- 邮件冒充：结合 SPF、DKIM、DMARC；正文保密/签名看 S/MIME。

#### 零信任不是“全拒绝”

核心是明确验证、最小权限、假设已失陷，并持续根据身份、设备状态、位置和风险调整访问。VPN 接入内网后仍不能自动获得所有系统权限。

### 今日原创题

**1.** ドメイン名を IP アドレスへ変換する仕組みはどれか。
ア DNS　イ DHCP　ウ NTP　エ SNMP

**2.** メール本文にドメイン署名を付け改ざんと送信ドメインを検証する仕組みはどれか。
ア SPF　イ DKIM　ウ RAID　エ VLAN

**3.** DMARC の役割として最も適切なものはどれか。
ア SPF/DKIM の結果と整合性に基づく処理方針・報告　イ ディスク暗号化　ウ IP 配布　エ 時刻同期

**4.** DMZ の目的はどれか。
ア 公開サーバと内部ネットワークを分離　イ 全端末へ管理者権限　ウ バックアップ削除　エ 著作権登録

**5.** SaaS 利用者にも残る責任として最も適切なものはどれか。
ア データ、アカウント、設定と利用管理　イ データセンター建物だけ　ウ 物理サーバ製造だけ　エ 一切ない

<details><summary>Day 11 答案</summary>

1. **ア**。DHCP 是分配网络参数。
2. **イ**。SPF 主要看授权发送来源，DKIM 验邮件域签名。
3. **ア**。DMARC 建立策略与反馈。
4. **ア**。公开区失陷时减少直达内网风险。
5. **ア**。SaaS 也不是责任归零。

</details>

## Day 12：服务、项目、采购与战略

### 高分补充

#### 服务管理时间线

服务中断先走 incident 恢复；反复发生建立 problem 查根因；修复需要改生产环境则走 change；涉及哪些服务器、版本和依赖关系由 configuration information 支撑。紧急变更可以简化流程，但仍须授权、记录和事后评审。

#### 采购安全

需求书定义安全、可用性、日志、数据位置和退出要求；选择时评价供应商能力；合同规定事件通报、再委托、审计、SLA、数据返还/销毁；服务中持续监视；退出时避免供应商锁定并验证数据删除。

### 今日原创题

**1.** 障害からサービスを迅速に復旧する活動はどれか。
ア 問題管理　イ インシデント管理　ウ 戦略管理　エ 著作権管理

**2.** 繰り返す障害の根本原因を分析する活動はどれか。
ア 問題管理　イ インシデント管理だけ　ウ 販売管理　エ DNS 管理

**3.** WBS の目的はどれか。
ア 作業を管理可能な単位へ階層分解　イ 組織の給与決定　ウ 通信暗号化　エ 法令改正

**4.** 緊急変更について適切なものはどれか。
ア 記録不要　イ 定めた緊急手順で承認し事後レビュー　ウ 誰でも無断実施　エ テストと回退を常に禁止

**5.** SWOT の外部環境に該当するものはどれか。
ア 強みと弱み　イ 機会と脅威　ウ 売上と費用だけ　エ 権限と認証

<details><summary>Day 12 答案</summary>

1. **イ**。恢复优先是事件管理。
2. **ア**。根因与永久解决是问题管理。
3. **ア**。WBS 分解工作，不是组织图。
4. **イ**。紧急不等于无控制。
5. **イ**。S/W 内部，O/T 外部。

</details>

## Day 13：科目 B 综合案例训练

### 案例

A 社的营业部使用云端客户管理系统。公司规定：员工只能使用个人账号；从公司外访问必须使用 MFA；含客户名单的文件不得保存于个人云盘；安全异常须立即报告 CSIRT。

员工甲为在家赶工，把客户名单上传到个人云盘，并把共享链接设为“知道链接的人均可查看”。随后甲收到一封自称云盘运营方的邮件，邮件要求“10 分钟内重新认证”，甲在链接页面输入了公司客户管理系统的账号和密码。第二天，监控发现甲的账号从海外 IP 大量导出客户记录。管理员先向甲询问，甲回答“可能是系统误报”。管理员没有停用账号，计划等甲到公司后再确认。两小时后导出仍在继续。

### 设问

**1.** 最初に優先すべき対応はどれか。
ア 甲への懲戒処分を決定する
イ 該当アカウントの利用を停止し、セッションを無効化して CSIRT に連絡する
ウ 全社員の PC を廃棄する
エ 翌月の定例会議まで待つ

**2.** 本案例中已经明确违反的规则有哪两项？请引用事实。

**3.** 直接导致客户管理系统账号泄露的攻击最可能是什么？
ア DDoS　イ フィッシング　ウ SQL インジェクション　エ ショルダーハッキング

**4.** 作为防止相同账号盗用再次发生的根本技术措施，哪项最恰当？
ア 公司内外均要求 MFA，并实施异常登录检测
イ 只提醒甲小心
ウ 删除所有日志
エ 允许共享账号

**5.** 为什么“先询问本人，等到公司后再处理”不恰当？

**6.** 个人云盘公开链接问题与系统账号盗用问题分别主要损害 CIA 中哪项？

<details><summary>Day 13 参考答案与证据链</summary>

1. **イ**。关键词是 `最初`；事实是海外 IP 导出仍在继续。先阻止损害扩大并启动正式响应。
2. ①“个人账号”规则相关：甲把公司系统凭据输入可疑页面，之后账号被滥用；更直接的明确违规是 ② 客户名单上传个人云盘，且设为任何有链接者可看；③ 发现异常后组织侧也未按“立即报告 CSIRT”执行。若要求员工甲的两项，可答个人云盘禁令和外部访问/认证规则需结合题干判断；不要虚构甲一定关闭了 MFA。
3. **イ**。紧迫措辞和伪运营方登录页是钓鱼。
4. **ア**。把外部访问规则扩展为一致的强认证，并加入异常检测；仅教育不是充分的技术根治。
5. 异常活动仍持续，等待会扩大泄露；本人否认不能推翻监控事实，应先遏制、保全证据、再调查。
6. 公开链接主要损害机密性；盗用本身涉及真实性/认证，恶意导出造成机密性损害，并破坏可追责判断。题目若只让各选一个，公开链接=机密性，冒充账号=真正性。

</details>

## 高分补遗：容易被基础笔记省略的考点

### 威胁情报与漏洞信息

| 术语 | 中文 | 考试结论 |
|---|---|---|
| CVE | 公共漏洞编号 | 识别同一漏洞，不表示严重度 |
| CVSS | 漏洞严重度评分体系 | 帮助排序，但还要结合本组织暴露与资产价值 |
| CWE | 常见软件弱点分类 | 描述弱点类型，不是具体产品漏洞编号 |
| JVN | 日本漏洞信息门户 | 获取日本相关漏洞与对策信息 |
| IOC | 入侵指标 | 恶意 IP、哈希、域名等已观察痕迹 |
| TTP | 战术、技术与过程 | 描述攻击者行为模式，比单一 IOC 更持久 |

严重度高不等于本组织优先级一定最高。外网暴露、是否正在利用、资产关键度、缓解措施和业务影响都会改变修补顺序。

### 物理安全纵深

- 区域按公开区、办公区、受限区、机房等分级；越深入控制越强。
- **共連れ（ともづれ）/ tailgating**：未授权者跟随授权者进入；门禁闸机、反尾随设计和员工教育组合应对。
- 来访者登记、证件可视、陪同、限定区域和离场回收。
- 机密纸张交叉粉碎；磁介质依据敏感度采用安全擦除、消磁或物理破坏。
- 清洁桌面和清洁屏幕降低无人时泄露；屏幕锁不能只靠员工自觉，可配自动锁定。
- UPS 应对短时停电与安全关机，发电机应对较长时间；两者用途不同。

### 移动办公与 BYOD

组织应决定是否允许 BYOD，并管理登记、补丁、加密、屏幕锁、公司/个人数据分离、备份、远程擦除、遗失报告和离职处置。MDM 能下发策略和远程控制，但不能自动解决员工隐私、法律和全部应用数据泄露。

公共 Wi-Fi 场景优先验证网络、使用受保护通信、禁用自动连接、避免敏感操作；VPN 保护通道，不保证终端本身无恶意软件。

### AI 与生成式 AI 使用风险

SG 可能把新技术放进传统控制框架考查：

- 把客户信息、源代码输入未获批准的外部生成式 AI，首先是数据外泄、目的外利用和合同风险。
- 输出可能存在错误、偏见和著作权问题，必须人工验证，不能因“AI 生成”免除责任。
- 应规定允许工具、允许数据、审批、日志、输出复核和事件通报。
- 防护重点仍是信息分类、供应商评估、访问控制、DLP、教育和监督，而不是另背一套孤立理论。

### IoT 与 OT

- 初始密码必须更换；禁用不必要服务；固件来源和签名需验证；资产清单和生命周期补丁不可缺。
- OT 首要考虑安全与可用性，不能未经验证直接套用会导致停机的 IT 补丁策略。
- 网络分段、允许列表、被动监视、维护窗口和供应商远程访问控制是典型措施。
- 设备停产后仍联网是生命周期风险，应规划替换或隔离。

### 数据脱敏与泄露防护

| 手段 | 说明 | 注意 |
|---|---|---|
| マスキング | 隐去部分值 | 用于显示与测试，仍需评估可识别性 |
| トークナイゼーション | 用无意义 token 替代敏感值 | 对照系统必须严密保护 |
| 暗号化 | 用密钥转换 | 密钥与数据同处会削弱效果 |
| 匿名加工 | 达到法定不可识别、不可复原要求 | 不是简单删姓名 |
| DLP | 识别并控制敏感数据流出 | 需分类、规则调优和例外流程 |

### 指标与报告

好指标应能支持决策，而非只追求“数字好看”。例如：关键补丁期限内完成率、钓鱼通报率、MFA 覆盖率、平均检测时间、平均遏制时间、恢复演练成功率、过期高权限账号数。单看“拦截攻击次数”可能因流量增加而上升，不能直接证明安全变差或变好。
